# 校园快取通 Campus Express

**版本：V1.0｜编制日期：2026-10-19｜面向：四川师范大学校园快递代取服务**

> 项目目标：把零散的校园快递代取需求集中到单一平台，支持预约、定价、统一收款、派单、配送确认、售后与财务对账。初期从一个校区的一个快递站和少量宿舍楼开始测试。本文件是产品需求与运营方案，不代表已获得校方、快递站或微信支付许可。

## 1. 项目定位与首批服务范围
- 服务名称（暂定）：校园快取通。未获得校方授权前，名称和图标不要暗示“学校官方服务”。
- 用户：在校学生、经审核的校园代取员、平台管理员。
- 首批覆盖：成龙校区**或**狮子山校区（任选一个启动）。只覆盖已确认允许授权代取的快递点和可合法配送区域。
- 服务内容：学生授权代取员在指定站点领取已到站快件，配送到校内指定交接地点，原则上不进入宿舍内部。
- 禁止代取：需要本人刷脸、实名现场查验、特殊保管条件或站点禁止代取的包裹；危险物品、违法物品；不接受拆包、倒卖、夹带等。

## 2. 三端最小可用功能（MVP）
### 学生端
1. 微信账号或手机快捷认证（须明示隐私条款）；首次选校区。
2. 填写快递站、快件数量、包裹规格、接收地点（宿舍楼下/校内交接点）、联系电话、取件码及备注；选择预约时间段。
3. 展示费用明细和预估送达时段；用户明确同意服务规则后下单。
4. 未接单可申请取消；支付后订单进入待派单队列；支付必须经过服务端验证成功才准派单。
5. 实时查看状态；服务端发送关键订单通知（需要对应消息订阅授权）；完成时采用收件验证码/双方确认，支持问题反馈、退款申请、评价。

### 代取员端
1. 提交申请，校内身份/联系方式审核，阅读服务协议；只有管理员审批后可接单。
2. 开关接单、查看附近或分配给自己的订单；一次只显示有权限的订单。
3. 接单后短暂展示取件码（默认隐藏）；记录到站、取件、在途、送达的操作时间；送达可使用收件验证码核验。
4. 查看有效收入、争议扣款与人工/正式支付渠道结算明细。

### 管理员端
1. 订单看板：待支付、待派单、待取件、配送中、待确认、完成、异常、退款。
2. 配送区域/快递站/时间段/价格维护；代取员审核、停用、派单和订单重新指派。
3. 退款审批、工单处理、用户反馈；财务记录与平台收入、代取员应付报酬统计。
4. 审计日志、订单导出、异常超时预警、敏感信息访问记录。

## 3. 标准流程与异常场景
学生填写订单 → 服务端报价 → 创建待支付订单 → 微信支付/试点测试支付 → 支付验证 → 待派单 → 代取员接单 → 领取包裹 → 配送中 → 交接验证码核验 → 完成 → 收入确认与代取员结算。

- 用户未支付：不派单；超时自动关闭订单。
- 无人接单：到达配置的时限后提示管理员补单或退款。
- 取件码错误/过期：代取员标记异常，提醒学生更新，不能臆测领取。
- 包裹丢失/破损：保留交接记录并立刻冻结订单结算，按明确的服务条款核实处理，不得单方面免责。
- 学生不在场：约定安全交接点或重新预约；禁止未经允许擅自放件。
- 用户取消：按代取员实际接单、到站、取件不同节点制定清晰退款规则，支付及退款状态以支付渠道服务端结果为准。
- 重复接单：服务端原子操作锁定，不能依赖前端按钮禁用。

## 4. 定价与财务模型（仅为待验证示例）
| 情形 | 学生参考价 | 说明 |
|---|---:|---|
| 普通包裹（首件） | ¥3 | 单点、指定范围内 |
| 大件首件 | ¥5 | 尺寸重量界限需公示 |
| 同订单加件 | +¥1/件 | 同站点同收件地址 |
| 加急 | +¥2 | 仅在有运力时开放 |

建议试点采用代取员每单基础报酬（例如¥2.2～¥2.5/普通单）+额外件补贴。每日先统计“完成单量 × 实收客单价 - 配送报酬 - 微信支付费用 - 退款损失 - 补贴 - 其他运营支出”。**毛利不是净利润**，不可仅按订单差价测算收益。

## 5. 必备数据表
- users：uid、角色、昵称、联系电话（加密/脱敏）、校区、账号状态。
- runners：uid、审核状态、服务区域、接单状态、信誉记录。
- pickup_locations：id、校区、站点名称、取件规则、开放状态。
- delivery_locations：id、校区、楼栋/交接点、可配送状态。
- orders：id、owner_uid、runner_uid、站点、配送位置、数量、规格、预约时间、报价快照、订单状态、创建时间、完成时间、异常原因。
- order_secrets：order_id、取件码密文、过期时间；只能本人及已分配并获授权的代取员读取，后台默认脱敏。
- payments：order_id、业务交易号、渠道交易号、金额（分）、支付状态、签名核验信息、回调幂等键。
- refunds：order_id、退款单号、金额（分）、原因、审核状态、渠道状态。
- settlements：runner_uid、订单id、应付金额、已付金额、打款凭据、状态。
- audit_logs：操作者、动作、目标、时间、元信息（不含原始取件码）。

## 6. 关键安全与隐私要求
- 不把取件码、手机号、身份证明信息公开显示在公共订单池、分享海报、日志或客服群里。
- 只收集必要个人信息；服务端细粒度角色权限与数据隔离；管理员访问敏感字段要有用途与记录。
- 传输全程HTTPS，隐私字段采用加密，支付密钥仅放服务端；按明确的保留期删去不再需要的取件码。
- 支付金额由服务端报价计算，不能直接信任客户端上传金额；支付结果以验签后的异步回调及主动查单为准。
- 所有“接单、退款、确认完成、结算”都要由服务端判定合法状态转换并防止重复请求。
- 制定隐私政策、用户服务协议、代取员协议和投诉渠道；使用前与校方和快递驿站确认代领制度。

## 7. 技术部署推荐路线（照顾零编程用户）
**路线A：验证需求。** 先用已搭建的可视化网页原型测试页面和订单流程；可临时采用测试订单/模拟付款，但不向公众宣称完成真实微信支付。收集用户反馈、确认具体站点和宿舍地点、招募测试代取员。

**路线B：正式微信小程序。** 注册/认证微信小程序，使用合规主体开通微信支付商户号，并绑定小程序APPID；接入微信支付下单、支付回调、查单、退款与账单。选择微信云开发或兼容的国内托管后端作为生产数据库与接口运行环境。完成交易类小程序订单发货管理适配（若适用）及平台审核后再公开上线。

注意：Base44 网页应用不等于微信小程序，也不自动提供微信支付许可；从网页原型迁移到原生小程序可能需要重新实现部分页面或后台接口。当前原型只用于设计和测试。正式支付能力需要微信后台审核与经营主体授权，不能靠前端“支付成功”提示代替。

## 8. 落地步骤与负责人
### 阶段 0：市场验证
- 实地找到合作快递站、询问可否凭授权取件、代取员需要什么凭据。
- 收集至少30名潜在学生的需求，记录愿意支付的价格、最需要的时间段。
- 找3~5名可靠的校园代取员测试；先覆盖1个站点、3~5栋宿舍。

### 阶段 1：测试版验收
- 至少10种场景：普通单、加件、大件、预约、取消、代取员拒绝、超时无人接单、错误取件码、重复点击支付、售后退款。
- 学生看不到别人的订单；代取员接单前看不到取件码；管理员保留必要的异常处理权限。
- 确认价格和运力；给用户清楚的交接、丢件、赔付和隐私说明。

### 阶段 2：正式收款和上线
- 准备主体资质、可用小程序账户及商户号。
- 完成支付与退款联调、订单及资金对账；少量内部实付测试。
- 上传代码、平台审核、提交隐私政策与所需资质；收到通过通知后公开二维码。

### 阶段 3：扩大运营
- 累计100+实单后评估接单率、准时送达率、投诉率、复购率和每单真实贡献毛利，再决定扩区。

## 9. 三个必须优先落实的问题
1. **合作点：** 具体哪个校区、哪些快递站允许他人授权代取？
2. **资金资质：** 是否已有可合法用于该业务的个体户/公司主体及微信支付商户号？没有则先做无真实收款测试。
3. **交付边界：** 只送宿舍楼下，还是可送到指定的校内交接点？是否有校园配送限制？
