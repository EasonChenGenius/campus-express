# V0.5 产品路线选择与 GitHub 参考

更新时间：2026-10-23。校园快取通仍是本机虚构数据演示；本文件记录产品选择和公开项目的可借鉴之处，不表示这些项目已经通过安全、合规或上线验收。

## 现在请负责人选择的三件事

| 决策 | 方案 A | 方案 B | 建议 |
|---|---|---|---|
| 首批服务范围 | 只做快递代取，流程清晰、现场规则较少 | 同时做代买、代送等综合跑腿，范围更大 | **A**；先完成单一业务的身份、站点、异常与结算闭环。 |
| 接单方式 | 代取员自愿抢单，超时由主管派单 | 系统自动派单，需准确排班、地理位置和可用运力 | **A**；保留人工兜底，待有真实运力数据后评估自动派单。 |
| 首批覆盖 | 每校区一个获准站点和一个核实苑区 | 两校区所有站点及苑区一起开放 | **A**；按校区分别核验，再逐个扩大。 |

这些选择只改变未来产品和实施顺序。任何方案都需要学校及站点许可、真实身份验证、隐私与安全验收；此刻不开放真实下单或支付。

## 前端、中间层、后台的优化顺序

1. **学生/代取员小程序：**先完成异常上报、代取员上线/下线与接单额度提示；随后完善订单状态解释、弱网提示、无障碍和真机体验。当前原生小程序可继续使用，无须仅为了换框架而重写。
2. **接口与业务中间层：**保留服务端校区隔离、状态机、幂等与原子接单；增加异常处理、时段容量、超时待办和可撤销的会话。封闭试用前接入微信服务端登录，将 `/api/demo/*` 从试用环境移除。
3. **后台与数据：**主管处理本校区异常、离线与接单上限、超时人工派单；总管理员查看双校区。试用环境迁移到具备备份、恢复与迁移机制的数据库，并建立监控、审计和受控后台登录。
4. **上线准备：**取得小程序主体及 AppID、站点和学校授权、HTTPS 域名、隐私告知与必要的合规材料；完成微信开发者工具、真机、弱网、权限和现场流程验收。支付在经营主体及商户资质落实后单独开发和验收。

## 本轮实际完成与仍待完成

V0.5 已在本机演示实现：代取员上线/下线、同时处理订单上限、异常订单上报与主管处理、30 分钟待接单提示。异常原因用固定选项，避免在演示中填写个人资料。`retry` 只允许尚未取件的订单重新开放接单；已取件订单需人工核实包裹去向。

仍需实现：**真实微信身份绑定、授权站点开关、按时段容量、自动提醒、正式数据库与备份、隐私与数据删除、真机验收、真实收款审批**。本机演示不构成封闭试用许可。
